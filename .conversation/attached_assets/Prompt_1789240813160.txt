# Build a Mobile Game: 4-Minute Math Challenge

Build a polished, fast, competitive, cross-platform mobile math game called **4-Minute Math Challenge**.

The core concept is simple:

> **Select an arithmetic operation → Select the number of digits → Solve as many problems as possible in 4 minutes → See your score → Compare yourself with other players.**

The app should prioritize **speed, simplicity, fairness, and competition**.

---

# 1. Core Game

Users compete to answer as many arithmetic questions correctly as possible within exactly:

**4 minutes / 240 seconds**

Before each game, the player selects:

### Arithmetic Operation

* ➕ Addition
* ➖ Subtraction
* ✖️ Multiplication
* ➗ Division

Only the selected operation is used during that game.

### Digit Level

The player then selects:

* 1 Digit
* 2 Digits
* 3 Digits
* 4 Digits

The selected digit level remains fixed for the entire game.

This creates **16 core competitive categories**:

**4 operations × 4 digit levels = 16 categories**

Examples:

* Addition / 1 Digit
* Addition / 4 Digits
* Subtraction / 2 Digits
* Multiplication / 2 Digits
* Multiplication / 4 Digits
* Division / 3 Digits

Scores from different categories must never be directly ranked against each other.

# 2. Number Generation

Create a reusable question-generation engine:

`generateQuestion(operation, digitLevel)`

Use these standard ranges:

1 Digit: 1–9
2 Digits: 10–99
3 Digits: 100–999
4 Digits: 1000–9999

Return a structure similar to:

{
operand1: 25,
operand2: 42,
operator: "×",
correctAnswer: 1050
}

Store digit ranges centrally so they can easily be modified later.

## Addition

Generate two operands using the selected digit range.

Example for 3 digits:

425 + 187

## Subtraction

Do not generate negative answers.

Always ensure:

operand1 >= operand2

Example:

723 − 418

Do not generate:

418 − 723

Negative-number support can be added later.

## Multiplication

Generate two operands using the selected digit range.

Example for 2 digits:

24 × 18

Make sure the answer input supports large integer results, especially for 4-digit multiplication.

## Division

Division must always produce a **whole-number answer**.

Never require decimal or fractional answers.

Never divide by zero.

Prefer generating the divisor and answer first and calculating the dividend.

For example:

divisor = 12
answer = 72
dividend = 864

Display:

864 ÷ 12

The generated question should respect the selected digit difficulty as closely and consistently as possible.

# 3. Pre-Game Screen

After choosing an operation and digit level, show a confirmation screen.

Example:

# Multiplication Challenge

**2 Digits**

You have **4 minutes**.

Answer as many questions correctly as possible.

Then show a large:

**START GAME**

button.

The timer must not start until START GAME is pressed.

---

# 4. Gameplay Screen

The gameplay interface must be extremely simple and optimized for **rapid answer entry**.

Display:

### 25 × 42

Then immediately below it show a large numeric answer input.

Also display the countdown timer prominently:

**03:42**

Optionally display the current correct-answer count without distracting the player.

The numeric keyboard should automatically be active when the game starts.

The player should not have to repeatedly tap the answer field.

Allow submission through:

* Large Submit/Enter button
* Keyboard Enter/Return action

After an answer is submitted:

1. Immediately validate it.
2. Record correct or incorrect.
3. Clear the input.
4. Generate the next question.
5. Automatically focus the answer field.
6. Keep the numeric keyboard open.

The next question should appear almost instantly.

Avoid animations or transitions that interfere with rapid entry.

---

# 5. Timer

Every competitive game lasts exactly:

**240 seconds**

Use a reliable game timer that cannot be manipulated simply by changing the device clock.

Display the remaining time prominently.

Example:

**02:47**

When the timer reaches zero:

* Stop accepting answers.
* Ignore unfinished answers.
* Do not generate another question.
* End the game automatically.
* Save the completed session.
* Display the results.

---

# 6. Scoring

For version 1:

**Score = Number of correct answers**

Track:

* Correct answers
* Incorrect answers
* Total attempted
* Accuracy
* Final score

Calculate:

`accuracy = correctAnswers / totalAttempted × 100`

Example:

Score: **47**

Correct: 47
Incorrect: 5
Attempted: 52
Accuracy: 90.4%

Build scoring as a separate module so future versions can support:

* Difficulty multipliers
* Speed bonuses
* Streak bonuses
* Incorrect-answer penalties
* Tournament scoring

# 9. Player Location

Capture the **general geographic location where the player is playing**.

Location is used for geographic leaderboards and future regional competitions.

Capture:

* City
* State / Region
* Country
* Country code

Example:

city: "Dallas"

region: "Texas"

country: "United States"

countryCode: "US"

Do **not** store or publicly expose precise GPS coordinates by default.

Location can be determined through:

1. Coarse device/IP location
2. User-selected location
3. Device location permission followed by reverse geocoding

If device location is used, convert the coordinates to city/state/country and discard the precise coordinates.

Clearly explain to users that general location is used for geographic rankings.

If the player declines location permission or location cannot be determined, allow manual city/state/country selection.

**Location must never be required to play the game.**

---

# 10. Location Per Game

Store general location with each completed game session.

Do not rely exclusively on the user's profile location because users may travel.

For example, someone living in Texas could play while visiting India.

That game can therefore contain:

city: "Thiruvananthapuram"

region: "Kerala"

country: "India"

countryCode: "IN"

This allows future features such as:

**Where did you play?**

and regional competitions.

Never publicly expose exact coordinates.

# 16. Ranking Rules

Rank using:

1. Highest correct-answer score
2. Highest accuracy
3. Fewest incorrect answers
4. Earlier completion timestamp

Implement ranking on the backend/database, not on the mobile client.

# 21. Anti-Cheat and Game Integrity

Because this is a public competitive leaderboard, **do not trust scores submitted directly by the mobile client**.

Players must not be able to simply call the database API and insert a score of 10,000.

Use secure server-side score processing.

Each competitive game should have a server-recognized session ID.

Record information such as:

* sessionId
* userId
* operation
* digitLevel
* server start timestamp
* server completion timestamp
* correct answers
* incorrect answers
* questions attempted
* duration
* score

Use server timestamps wherever practical.

Validate that:

* The session is legitimate.
* The session hasn't already been submitted.
* Duration is approximately 240 seconds.
* Question counts are plausible.
* The score matches the submitted/validated answers.
* The user owns the game session.

Ideally, the server should generate or cryptographically validate the question sequence so a modified client cannot simply claim arbitrary correct answers.

Design this carefully enough that future prize-based competitions could use stronger server-authoritative validation.

# 22. Database Security

Use Supabase:

* Authentication
* PostgreSQL
* Row Level Security
* Database functions/RPC where appropriate
* Edge Functions where appropriate

Users should be able to:

* Read public leaderboard data.
* Read their own complete game history.
* Update permitted parts of their own profile.

Users should **not** be able to:

* Change another user's profile.
* Modify another user's games.
* Directly alter leaderboard scores.
* Change completed competitive games.
* Submit arbitrary scores.

Design and document all Row Level Security policies.

* userId
* operation
* digitLevel
* score
* accuracy
* incorrectAnswers
* completedAt
* countryCode
* region
* city

Do not download thousands of game records to the phone and calculate rankings locally.

Filtering, personal-best selection, aggregation, and ranking should happen server-side.

Design for eventual growth to a large number of users and game sessions.

# 28. Offline and Connectivity Behavior

The game should handle temporary network interruptions gracefully.

A player should not lose an active game merely because connectivity briefly drops.

However, competitive leaderboard submission must be securely validated once connectivity is available.

Clearly distinguish between:

* Game completed
* Score pending validation
* Score validated
* Score rejected

Never silently place an unvalidated score on the public leaderboard.

# 31. Implementation Process

Do **not** immediately generate a large amount of code.

First provide a technical design containing:

1. Overall architecture
2. Screen/navigation map
3. UI component structure
4. PostgreSQL database schema
5. Database relationships
6. Required database indexes
7. Authentication flow
8. Location-capture strategy
9. Game-state model
10. Question-generation algorithms for all four operations
11. Timer implementation
12. Score calculation
13. Game-session lifecycle
14. Leaderboard architecture
15. Geographic leaderboard queries
16. Personal-best query strategy
17. Anti-cheat strategy
18. Supabase Row Level Security policies
19. Edge Functions/API contracts
20. Offline/connectivity strategy

Identify any architectural or security concerns before implementation.

Then implement the application incrementally in this order:

**Phase 1:** Project structure and navigation

**Phase 2:** Authentication and profiles

**Phase 3:** Operation and digit selection

**Phase 4:** Math question-generation engine with automated tests

**Phase 5:** 4-minute gameplay engine

**Phase 6:** Results and personal bests

**Phase 7:** Database persistence

**Phase 8:** Location

**Phase 9:** Leaderboards

**Phase 10:** Anti-cheat/server validation

**Phase 11:** My Scores and My Games

**Phase 12:** UI polish, accessibility, testing and error handling

For every phase:

* Explain the implementation.
* Generate production-quality code.
* Include required database migrations.
* Include tests for important business logic.
* Identify files being created or modified.
* Do not use mock implementations where real implementation is practical.

At completion, provide:

* Complete source code
* Database migrations
* Supabase configuration
* Environment-variable template
* Setup instructions
* Local development instructions
* iOS run instructions
* Android run instructions
* Testing instructions
* Production deployment/build instructions

The final result should be a **working mobile application**, not merely a prototype or collection of mock screens.
